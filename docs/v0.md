# V0: an inspectable intent compiler

## Decisions

The merged foundation already separates source origin from user review. Keep its
flat `items` collection rather than introduce parallel mutable
objective/context/ assumptions fields. Item kinds give the five core intent
dimensions. Assumptions are the inferred/default subset; unknowns are separate
data with no asserted value. The foundation's `source_reported` origin is also
retained for supplied evidence.

Only three fields were added: item confidence, unknown effect, and suggested
choices. The schema is still experimental, now `0.1.1-draft`. The revision is
versioned explicitly; old records need a version-only migration before reading.

Confidence is an uncalibrated estimate. It cannot elevate a compiler proposal
into a user requirement. Quick mode means “no interaction, expose proposals and
gaps,” not blanket acceptance. A user can separately confirm or delegate a
scoped item with the existing `decide` operation. Required gaps continue to
block their named steps even after other proposals are accepted.

The new modules are `extract.ts` (offline/profile and semantic boundary),
`provider.ts` (optional transport), `clarify.ts` (selection and scoped answers),
`compile.ts` (two wrappers around the existing export), and `benchmark.ts`
(model-visible packet preparation). No plugin framework or gateway is necessary.

## Extraction boundaries

`parse` defaults to a deliberately narrow, deterministic demonstration. It keeps
the entire request as a literal objective, proposes a report format, and records
missing evidence/scope. Only the exact “Add subscriptions.” demo triggers
billing questions. This restriction avoids naïve keyword handling of “do not add
subscriptions,” but does not solve general language interpretation. It is useful
for exercising the pipeline, not judging semantic extraction quality.

`parse --provider chat` calls an exact chat-completions endpoint supplied by the
caller. Local endpoints need no account. Hosted endpoints may charge; Intentacle
has no preferred provider or default hosted URL. Model/server installation is
external. The integration uses plain JSON text instead of assuming support for
JSON-schema response modes. The provider interface accepts a function, so
another transport can be implemented without changing the contract or compiler.

The extractor receives the scaffold and full JSON Schema. Deterministic checks
reject malformed output, invalid provenance, changed references/identity, fake
answers, confirmed assumptions, or resolved unknowns/conflicts. Explicit items
must quote user text verbatim; paraphrases must remain inferred. This is an
intentionally conservative boundary, not semantic entailment verification. It
can still miss requirements or extract a misleading substring. Inspect the
record before handing it off. Failures are errors, with no hidden repair call or
fallback. The original input remains with the caller; no success artifact is
written after a failed extraction.

Provider transport is tested against a real loopback HTTP mock, including
invalid and oversized responses, errors, redirects, and timeouts. No actual
local model or proprietary endpoint has been evaluated in this implementation
session.

## Clarification

`clarify task.json --step execute` returns a single batch of at most three
questions: required ones affecting that step first, then important ones with a
recorded consequence. It returns overflow IDs, other deferred gaps, open
conflicts, and inspectable gaps separately. Optional questions do not interrupt
and irrelevant questions are omitted from the record. The small
`classifyNecessity` helper maps relevance/blocking/materiality judgments to
categories; the extractor or human must still make those semantic judgments.

Apply one to three literal answers using `clarify --answers answers.json`. Each
answer is scoped to one unknown and stored as a new supplied user-answer
reference. Answers are not parsed into new requirements, and no model interprets
consent. The caller chooses `answer` only when the text resolves that entire
question. Use `defer` for partial answers, uncertainty, or “use best judgment.”
Deferral preserves the open unknown and blocker, while retaining the text. A
path answer identifies intended source; it does not prove source availability.

Conflicts are exposed, not automatically resolved. Existing schema-supported
manual resolution remains available; a conflict-resolution UI is outside V0. The
interface is a structured CLI batch, not an interactive terminal questionnaire.

## Compilation

`compile --target generic` and `compile --target codex` consume the same
validated record. Neither calls a model, changes assumptions, or resolves
unknowns. Every export includes raw references, origin, review, confidence when
supplied, unknowns, effects, choices, and current resolutions. The Codex wrapper
adds repository inspection and actual-verification reporting guidance,
explicitly identified as adapter guidance rather than attributed to the user.

`--json` includes instructions plus coverage, target/compiler versions,
readiness, and a SHA-256 hash of `JSON.stringify(record)`. The hash detects
changes in the serialized record; it is not a JSON canonicalization standard or
signature. `--require-ready` checks the record's `next_step`, not a universal
readiness flag. Inspection may be possible while implementation remains blocked.
Ordinary compile can export a blocked task for review, with blockers prominent.

The adapter boundary proves mechanical recompilation only. Whether the Codex
wrapper helps downstream results is an untested hypothesis.

## Comparison discipline

Prompt Master is the primary existing-tool baseline for this V0. Its current
[documented workflow](https://github.com/nidhinjs/prompt-master) extracts prompt
dimensions, limits clarification, and produces target-oriented output. That is
evidence of adjacent functionality, not a measured win or loss for Intentacle.
Use real pinned tool output in the harness; never implement a weak imitation and
call it the baseline. The harness retains missing arms, failures, and unscored
metrics. See [benchmark instructions](../benchmark/README.md).
